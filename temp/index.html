Diagnostic: HTTPS requests get redirected to HTTP

A live reproduction for phpwebhosting support, on andoverct.info. This page and everything under /temp/ exists only for the support ticket and will be deleted afterwards.

The request to try

curl -sSI https://andoverct.info/temp/no-slash-demo

That path is a real directory, so Apache issues its usual trailing-slash redirect. Here is what comes back:

ExpectedLocation: https://andoverct.info/temp/no-slash-demo/
ActualLocation: http://andoverct.info/temp/no-slash-demo/

The client asked for HTTPS, and Apache answered with a redirect to plain HTTP. Your front end then redirects that back to HTTPS, so a browser or curl ends up in the right place after an extra hop and the problem is invisible in normal use. Clients that refuse an HTTPS → HTTP downgrade see a redirect loop and fail outright.

Why it happens

env.php shows the request environment as Apache receives it. Every signal Apache could use to tell that the original request was HTTPS is missing:

X-Forwarded-Proto: (absent)
X-Forwarded-Ssl:   (absent)
Front-End-Https:   (absent)
HTTPS:             off
SERVER_PORT:       80

The cause: the SSL front end terminates TLS and proxies to Apache over plain HTTP without passing any protocol information. Apache therefore believes it is serving HTTP, and every redirect it generates for itself — mod_dir's trailing-slash redirect, and any RewriteRule with a relative target or %{REQUEST_SCHEME} — is built with an http:// scheme.

What would fix it

Have the front end add a protocol header when it proxies to Apache. Any one of these is enough:

X-Forwarded-Proto: https
X-Forwarded-Ssl: on
Front-End-Https: On

With any of them present, one line of .htaccess restores correct behaviour site-wide and no further changes are needed:

SetEnvIf X-Forwarded-Proto https HTTPS=on

What we are doing in the meantime

The rest of the site is worked around: every self-referential redirect names https://andoverct.info explicitly, repeated in each subdirectory that enables mod_rewrite, since per-directory rewrite rulesets are not inherited. That is why you will not see this problem anywhere else on the site — /temp/ deliberately declares RewriteEngine On with no rules, which switches the workaround off for this directory so the original behaviour is observable.

The workaround is verbose and easy to regress as the site grows, which is why we would prefer the header. If the front end configuration is global to the shared-hosting platform rather than per account, we understand — in that case, is there any per-account way to have the protocol passed through?

Compare against the rest of the site

curl -sSI https://andoverct.info/temp/no-slash-demo   # http://  ← the bug
curl -sSI https://andoverct.info/reports              # https:// ← worked around

Both are directories; both trigger the same trailing-slash redirect. The only difference is whether our workaround is active.
